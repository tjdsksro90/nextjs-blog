블로그 글을 MDX로 쓰기로 하고 처음에는 Next.js 공식 패키지인 `@next/mdx`로 시작했다. 페이지 하나를 MDX로 만드는 건 금방 됐는데, "블로그"를 만들려고 하니 직접 짜야 할 것이 계속 늘어났다. 그래서 `fumadocs-mdx`와 비교해 보고 갈아탔다.

## 비교

두 도구 모두 `.mdx` 파일을 React 컴포넌트로 바꿔 준다. 차이는 **그 다음을 누가 맡느냐**다.

|                            | @next/mdx             | fumadocs-mdx              |
| -------------------------- | --------------------- | ------------------------- |
| MDX → 컴포넌트             | O                     | O                         |
| 글 폴더를 읽어 목록 만들기 | 직접 구현             | 컬렉션으로 정의하면 자동  |
| frontmatter 검사           | 직접 구현             | zod 스키마로 빌드 때 검사 |
| 목차(TOC)                  | 직접 구현 (제목 파싱) | 빌드 때 자동 생성         |
| 코드 하이라이트, GFM       | 플러그인 직접 설정    | 기본 포함 (shiki)         |
| 화면(UI)                   | 자유                  | 자유 (fumadocs-ui는 선택) |

`@next/mdx`는 "MDX를 페이지로 쓸 수 있게 해 주는 연결 장치"에 가깝고, `fumadocs-mdx`는 "MDX 글을 콘텐츠 데이터로 다루게 해 주는 도구"에 가깝다.

## 장단점

### @next/mdx

**장점**

- Next.js 공식이라 문서가 Next 문서 안에 같이 있고, 버전이 바뀌어도 따라가기 쉽다.
- 설정이 거의 없다. `page.mdx` 하나 만들면 바로 페이지가 된다.
- About 페이지처럼 **글 하나짜리 페이지**에는 이걸로 충분하다.

**단점**

- 글 목록, 정렬, 초안 처리, 목차를 전부 직접 만들어야 한다.
- frontmatter를 읽으려면 remark 플러그인을 따로 붙여야 하고, 값이 틀려도 아무도 알려 주지 않는다. `date`를 빠뜨리면 목록에서 날짜가 조용히 비어 있을 뿐이다.
- Turbopack에서는 remark/rehype 플러그인을 함수가 아니라 **문자열 이름**으로 넘겨야 하는 제약이 있어서 설정이 헷갈렸다.

### fumadocs-mdx

**장점**

- `defineCollections`로 글 폴더를 정의하면 글 목록이 알아서 모인다.
- frontmatter 규칙을 zod 스키마로 적어 두면, 틀린 글이 있을 때 **빌드가 실패**한다. 배포된 뒤에 깨진 글을 발견할 일이 없다.
- 목차, 코드 하이라이트, 제목 id 같은 블로그 기본기가 이미 들어 있다.
- 헤드리스로 쓸 수 있다. 로직(`fumadocs-core`)만 가져오고 화면은 전부 직접 만든다.

**단점**

- ESM 전용이라 `next.config.ts`를 `next.config.mts`로 바꿔야 했다. (Node 22.18 이상 필요)
- 빌드할 때 `.source` 폴더에 파일을 생성한다. 이 폴더는 git과 lint 대상에서 빼 줘야 한다.
- 원래 문서 사이트용 도구라, 블로그에 딱 맞는 예제는 적다. 공식 문서의 문서 사이트 예제를 블로그에 맞게 바꿔 읽어야 한다.

## 선택 기준

결국 이 질문으로 정리됐다.

> 글이 하나인가, 여러 개인가?

- **글 하나짜리 페이지**(About, 소개 페이지) → `@next/mdx`로 충분하다.
- **목록, 태그, 목차가 필요한 글 모음**(블로그, 문서) → 직접 짤 코드가 많아지므로 `fumadocs-mdx`가 낫다.

내 블로그는 글이 계속 늘어나고 목록, 태그, 목차가 다 필요하다. 그리고 화면은 직접 만들고 싶었는데, fumadocs는 헤드리스로 쓸 수 있어서 디자인 자유도를 잃지 않는다. 이 두 가지로 fumadocs-mdx를 골랐다.

<Callout type="tip" title="둘 다 쓸 수도 있다">
  지금 블로그의 About 페이지는 `app/about/page.mdx`로 되어 있다. fumadocs-mdx로 바꾼 뒤에도 페이지 하나짜리 MDX는 그대로
  쓸 수 있다.
</Callout>

## 마무리

- `@next/mdx`는 **MDX를 페이지로**, `fumadocs-mdx`는 **MDX를 데이터로** 다룬다.
- 글이 여러 개고 목록과 검사가 필요하면 fumadocs-mdx가 직접 짤 코드를 많이 줄여 준다.
- 헤드리스로 쓰면 화면은 지금처럼 직접 만들 수 있다.

다음 글에서는 fumadocs로 글 컬렉션을 정의하고 홈에 글 목록을 띄운 과정을 정리한다.
